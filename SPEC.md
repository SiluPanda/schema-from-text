# schema-from-text -- Specification

## 1. Overview

`schema-from-text` is a code generation library that takes a natural language description of a data structure and produces validated Zod schemas, JSON Schema objects, and TypeScript type declarations via any LLM. It accepts a plain English string like "a user with name, email (must be valid email), and optional age (number, 0-150)" and returns syntactically correct, validated output in one or more schema formats -- ready to use in application code, tool definitions, form validators, or API contracts.

The gap this package fills is specific and well-documented. Developers building AI-powered applications constantly need schemas -- for tool parameter definitions (OpenAI function calling, Anthropic tool use, MCP tools), for structured output constraints, for form validation, for API request/response contracts. Writing these schemas by hand is tedious and error-prone, especially for complex nested structures with arrays, enums, optional fields, and format constraints. The current workflow is: think about the structure, open a Zod/JSON Schema reference, manually write the schema code, fix syntax errors, test it, iterate. For a moderately complex schema (a user profile with nested addresses, phone numbers, and role enums), this takes 10-20 minutes. Natural language is faster: describe what you want in one sentence, get a validated schema back in seconds.

Developers already use ChatGPT or Claude to generate schemas, but the workflow is manual: open a chat, type the description, copy the generated code, paste it into the project, fix any issues, repeat. No package automates this pipeline with validation, retry on failure, and direct programmatic output. `json-schema-generator` infers schemas from example JSON data -- it requires a concrete example, not a description, and produces only JSON Schema. `ts-to-zod` converts TypeScript types to Zod schemas -- it requires an existing TypeScript type, not natural language. `zod-to-json-schema` converts Zod schemas to JSON Schema -- it operates on existing schemas, not descriptions. None of these tools go from natural language to schema.

`schema-from-text` provides a `generateSchema` function that takes a description string and an LLM function, constructs a prompt optimized for schema generation, calls the LLM, parses and validates the output, retries with error feedback if the output is invalid, and returns the validated schema. It supports three output formats: Zod code (a string containing valid Zod schema code like `z.object({ name: z.string(), ... })`), JSON Schema (a valid JSON Schema object conforming to draft-07 or draft-2020-12), and TypeScript type declarations (an interface or type alias). It supports schema refinement -- taking an existing generated schema and a modification instruction ("add a required role field with enum values admin, user, guest") and producing an updated schema. The LLM interface is a simple function `(prompt: string) => Promise<string>`, making it usable with any provider: OpenAI, Anthropic, Google, Mistral, Ollama, or any custom inference server.

The package composes with other packages in this monorepo. `schema-bridge` converts schemas between provider-specific formats -- `schema-from-text` generates the schema from text, then `schema-bridge` converts it to the format a specific provider expects. `llm-retry` provides retry orchestration with validation feedback -- `schema-from-text` uses the same pattern internally (call LLM, validate output, retry with error feedback) and can optionally delegate to `llm-retry` for the retry loop. `tool-output-guard` validates tool output against schemas at runtime -- schemas generated by `schema-from-text` can be passed directly to `tool-output-guard` for runtime validation.

## 2. Goals and Non-Goals

### Goals

- Provide a `generateSchema(description, options)` function that takes a natural language description of a data structure and an LLM function, and returns validated schema output in one or more formats (Zod code, JSON Schema, TypeScript type).
- Provide format-specific convenience functions -- `generateZod(description, options)`, `generateJSONSchema(description, options)`, `generateTypeScript(description, options)` -- that return output in a single format.
- Provide a `refine(schema, modification, options)` function that takes an existing generated schema and a natural language modification instruction, and returns an updated schema with the modification applied.
- Provide a `createGenerator(config)` factory that returns a preconfigured `SchemaGenerator` instance for repeated use with different descriptions, avoiding repeated configuration of the LLM function, retry settings, and output format.
- Validate all generated output before returning it. For Zod code: parse the code string to check syntax validity. For JSON Schema: validate against the JSON Schema meta-schema. For TypeScript: check for balanced braces, valid type syntax, and parseable declarations.
- Retry with error feedback when generated output is invalid. Construct a feedback message containing the validation errors and the invalid output, append it to the conversation, and re-call the LLM. This follows the same pattern as `llm-retry` but is specialized for schema generation.
- Support a configurable maximum number of retries (default: 3). Return a detailed result object containing the validated schema, the number of attempts, whether retry was needed, and on failure, the validation errors and raw output from each attempt.
- Be provider-agnostic. Accept any `(prompt: string) => Promise<string>` function for the LLM call. No dependency on any LLM provider SDK.
- Provide a CLI that accepts a description string or file and outputs the generated schema to stdout or a file.
- Keep runtime dependencies minimal. `zod` as an optional peer dependency (required only for Zod code validation at generation time). No other runtime dependencies.

### Non-Goals

- **Not an LLM client.** This package does not make HTTP requests, manage API keys, handle authentication, or parse provider-specific response envelopes. The caller provides a function that calls the LLM and returns the raw text output. Use the OpenAI SDK, Anthropic SDK, or any HTTP client to make the actual API call.
- **Not a schema conversion library.** This package generates schemas from text. It does not convert between schema formats (Zod to JSON Schema, JSON Schema to TypeBox, etc.). For schema conversion, use `schema-bridge`. The two packages are complementary: `schema-from-text` creates the schema, `schema-bridge` converts it to provider-specific formats.
- **Not a TypeScript compiler or type checker.** The TypeScript output format produces type declaration strings. It does not type-check them against a project's `tsconfig.json`, resolve imports, or integrate with the TypeScript compiler API. The generated TypeScript is syntactically validated but not semantically analyzed.
- **Not a runtime validator.** This package generates schema definitions. It does not validate data against those schemas at runtime. For runtime validation, use the generated Zod schema with `schema.parse()` or `schema.safeParse()`, or use `tool-output-guard`.
- **Not a schema inference tool.** This package does not infer schemas from example data (JSON objects, CSV rows, database records). It generates schemas from human-written natural language descriptions. For inference from examples, use `json-schema-generator` or similar tools.
- **Not a prompt engineering framework.** The prompts used internally are optimized for schema generation but are not user-configurable in their entirety. The caller controls the description and output format, not the system prompt or few-shot examples. For general prompt engineering, use `prompt-lint` or `prompt-optimize`.

## 3. Target Users and Use Cases

### AI Application Developers Defining Tool Parameters

Developers building applications with tool/function calling (OpenAI, Anthropic, MCP, Vercel AI SDK) who need parameter schemas for every tool. A developer adding a "search_products" tool needs a schema for its parameters: query string, category enum, price range, sort order. Instead of writing the Zod or JSON Schema by hand, they describe it in natural language and get a validated schema back. A typical integration: `const { code } = await generateZod("search parameters: query (string, required), category (one of electronics, clothing, books), priceMin and priceMax (numbers, optional, min 0), sortBy (one of relevance, price_asc, price_desc, default relevance)", { llm })`.

### Rapid Prototypers and Hackathon Developers

Developers building MVPs or hackathon projects who need schemas quickly and do not want to spend time on manual schema authoring. They describe their data model in plain English -- "a blog post with title, body, author name, tags array, published boolean, created date string" -- and get working Zod schemas they can drop directly into their Vercel AI SDK tools or API routes. Speed matters more than hand-tuned precision for this use case.

### Backend Developers Building API Contracts

Developers defining API request and response schemas for REST or GraphQL services. They describe the shape of an API response -- "a paginated response with items array of products (each with id, name, price, imageUrl), total count, page number, page size, and hasNextPage boolean" -- and get JSON Schema for OpenAPI documentation or Zod schemas for runtime validation middleware.

### Form and Validation Engineers

Developers building complex forms who need validation schemas. A form for user registration might need: "email (valid email, required), password (string, min 8 chars, must contain a number and uppercase letter), confirm password (must match password), name (string, 2-50 chars), phone (optional, must match phone format), date of birth (date string, must be at least 18 years ago)". Generating the Zod schema for this by hand requires remembering the API for `.email()`, `.min()`, `.regex()`, and custom refinements. Describing it in natural language is faster.

### Database Model Designers

Developers designing database models who want to quickly prototype the schema before implementing it in Prisma, Drizzle, or another ORM. They describe the entity -- "an order with orderId (UUID), customerId (UUID), items array (each with productId, quantity integer min 1, unitPrice number), status enum (pending, processing, shipped, delivered, cancelled), createdAt and updatedAt timestamps" -- and get a TypeScript type or Zod schema that serves as a starting point for the ORM model.

### Teams Adopting Schema-First Development

Teams transitioning to schema-first development where the schema is the source of truth for types, validation, API docs, and tool definitions. These teams need to bootstrap schemas for existing untyped data structures. A tech lead describes each entity in the system ("a customer with name, email, subscription tier, billing address, payment methods array") and generates the initial schemas that the team then refines and maintains.

## 4. Core Concepts

### Description

The description is the natural language input provided by the user. It describes a data structure in plain English, including field names, types, constraints, optionality, and nesting. Descriptions range from simple ("a user with name and email") to complex ("an e-commerce order with nested line items, each containing a product reference with SKU, quantity with minimum 1, unit price, and discount percentage between 0 and 100, plus shipping address with street, city, state as a US state enum, and zip code matching a 5-digit pattern"). The quality of the generated schema depends directly on the specificity of the description. Ambiguous descriptions ("a thing with some data") produce generic schemas. Specific descriptions with explicit types, constraints, and structure produce precise schemas.

### Output Format

The output format determines what kind of schema is generated. Three formats are supported:

- **Zod code**: A string containing valid Zod schema code. Example: `z.object({ name: z.string(), age: z.number().int().min(0).max(150).optional() })`. This is the most expressive format, supporting refinements, transforms, and Zod-specific features. The output is a code string, not an instantiated Zod schema object -- it can be written to a file, `eval`'d, or used in code generation pipelines.
- **JSON Schema**: A valid JSON Schema object (draft-07 or draft-2020-12). Example: `{ "type": "object", "properties": { "name": { "type": "string" }, "age": { "type": "integer", "minimum": 0, "maximum": 150 } }, "required": ["name"] }`. This is the most portable format, usable with any validation library (ajv, JSON Schema Validator) and accepted by LLM providers for structured output.
- **TypeScript type**: A TypeScript interface or type alias declaration. Example: `interface User { name: string; age?: number; }`. This is useful for type-safe code generation and documentation. It does not include runtime validation logic.

### Generation Pipeline

The generation pipeline is the sequence of steps that transforms a description into a validated schema. It involves prompt construction, LLM invocation, output parsing, validation, and optional retry with error feedback. The pipeline is the same regardless of output format -- only the prompt instructions and validation logic differ per format.

### Schema Validation

Schema validation is the process of verifying that the LLM-generated output is syntactically and structurally correct for its target format. Validation catches common LLM output issues: syntax errors in Zod code (missing parentheses, undefined methods), invalid JSON Schema (wrong `type` values, malformed `$ref`), and broken TypeScript syntax (unclosed braces, invalid type expressions). Validation is the gatekeeper between the LLM's raw output and the caller's application code.

### Schema Refinement

Schema refinement is the process of modifying an existing generated schema based on a natural language instruction. The LLM receives the current schema and a modification instruction, and produces an updated schema. Refinement supports iterative schema development: generate a base schema, then refine it step by step ("add email validation", "make age required", "add an addresses array"). Each refinement produces a new validated schema.

### LLM Function

The LLM function is the caller-provided function that invokes the language model. It is typed as `(prompt: string) => Promise<string>` -- the simplest possible interface. The caller wraps their provider SDK call in this function. `schema-from-text` constructs the prompt (system instructions + description + format constraints), passes it to the LLM function, and receives the raw text output. This abstraction makes the package provider-agnostic.

### Step 1: Parse Description

The description string is preprocessed before prompt construction. Preprocessing normalizes whitespace (collapse multiple spaces, trim), detects structural hints that inform the prompt (keywords like "array of", "list of", "nested", "optional", "required", "enum", "one of"), and identifies explicit type annotations ("string", "number", "boolean", "date"). This preprocessing does not modify the description -- it extracts metadata that helps the prompt construction step produce more targeted instructions.

For example, if the description contains "array of addresses, each with street, city, and zip", the parser detects a nested array-of-objects pattern and can include more specific few-shot examples for that pattern in the prompt.

### Step 2: Construct Prompt

The prompt is constructed from four components:

1. **System instruction**: A role description ("You are a schema generator") plus format-specific rules (what Zod API is available, what JSON Schema draft to use, what TypeScript syntax conventions to follow).
2. **Few-shot examples**: Two or three examples of description-to-schema conversion, selected based on the structural hints detected in Step 1. If the description involves nested objects, examples include nested object schemas. If it involves enums, examples include enum schemas.
3. **User description**: The caller's description string, presented as the task to perform.
4. **Output constraint**: A strict instruction to output only the schema code/JSON with no explanation, no prose, no markdown fences. This minimizes the need for extraction in Step 4.

The prompt is assembled into a single string and passed to the LLM function. The prompt is not a multi-message conversation -- it is a single string because the LLM interface is `(prompt: string) => Promise<string>`, not a messages-based API. The caller can use a messages-based API internally by wrapping the prompt as a user message in their LLM function.

### Step 3: Call LLM

The LLM function is invoked with the constructed prompt. The function returns the raw text output from the LLM. This step is entirely opaque to `schema-from-text` -- the caller controls the model, temperature, max tokens, and all other generation parameters through their LLM function.

### Step 4: Extract Schema

The raw LLM output is processed to extract the schema content. Even with explicit instructions to output only the schema, LLMs frequently wrap output in markdown code fences, prepend explanatory text ("Here is the schema:"), or append notes ("This schema validates..."). The extraction step handles these cases:

1. **Markdown fence stripping**: If the output contains a code fence (` ```typescript ... ``` `, ` ```json ... ``` `, or bare ` ``` ... ``` `), the content inside the fence is extracted.
2. **JSON extraction**: For JSON Schema output, if the output contains a JSON object embedded in surrounding text, the JSON is extracted using bracket matching (find the first `{`, match to its closing `}`).
3. **Prose removal**: For Zod and TypeScript output, if the output starts with prose before the code, the code portion is identified by looking for the first line starting with `z.`, `import`, `interface`, `type`, or `export`.
4. **Trailing content removal**: Any text after the schema (explanations, notes, usage examples) is removed by detecting the end of the schema code/JSON.

### Step 5: Validate

The extracted output is validated according to the target format.

**Zod code validation:**
- Parse the code string as a JavaScript expression. This catches syntax errors like unmatched parentheses, missing commas, and undefined variables.
- Check that the code references only valid Zod methods (`z.object`, `z.string`, `z.number`, `z.boolean`, `z.array`, `z.enum`, `z.union`, `z.literal`, `z.optional`, `z.nullable`, `z.tuple`, `z.record`, `z.discriminatedUnion`, `z.lazy`, and their chainable methods like `.min()`, `.max()`, `.email()`, `.url()`, `.regex()`, `.refine()`, `.optional()`, `.nullable()`, `.default()`, `.describe()`, `.transform()`).
- Optionally (when `validate: 'eval'` is set and `zod` is installed), evaluate the code string in a sandboxed context with `zod` available, producing an actual Zod schema object. This catches runtime errors that syntax parsing misses (e.g., `.email()` called on a non-string schema).

**JSON Schema validation:**
- Parse the output as JSON. This catches malformed JSON (trailing commas, unquoted keys, single quotes).
- Validate the parsed object against the JSON Schema meta-schema. This catches structural errors (invalid `type` values, malformed `properties`, missing `type` on object schemas). The meta-schema validation uses a lightweight built-in validator that checks the most common structural requirements without requiring `ajv` as a dependency.
- Check that `required` arrays reference only properties that exist in `properties`.
- Check that `$ref` pointers (if any) resolve to definitions in `$defs` or `definitions`.

**TypeScript type validation:**
- Check for balanced braces (`{}`), brackets (`[]`), and angle brackets (`<>`).
- Check that the declaration starts with `interface`, `type`, or `export`.
- Check that property declarations follow valid TypeScript syntax (name followed by `:` or `?:` followed by a type expression).
- Check that type expressions use valid TypeScript types (`string`, `number`, `boolean`, `null`, `undefined`, arrays with `[]` suffix, object literals, union types with `|`, intersection types with `&`).

### Step 6: Format Errors

When validation fails, the errors are formatted into a feedback message that gives the LLM actionable information for correction.

For each validation error, the feedback includes:
- What was wrong (e.g., "Syntax error at position 45: unexpected token ')'")
- What was expected (e.g., "Expected a closing parenthesis to match the opening parenthesis at position 12")
- A correction hint when applicable (e.g., "The method .email() can only be chained on z.string(), not z.number()")

The feedback message also includes the invalid output so the LLM can see exactly what it produced and make targeted corrections.

### Step 7: Retry with Error Feedback

The prompt is reconstructed to include the original description, the invalid output, and the validation errors. The LLM is called again with this expanded prompt. The retry prompt follows this structure:

```
Your previous attempt to generate a [Zod schema / JSON Schema / TypeScript type] had the following errors:

[numbered error list]

Your previous output was:
[invalid output]

Please fix these errors and generate a valid [format] for the original description:
[original description]

Output ONLY the corrected schema, no explanation.
```

The retry loop continues until validation succeeds or the maximum retry count is reached. Each attempt is recorded in the result's `attempts` array.

## 6. Output Formats

### Zod Code

**What is generated:** A string containing a valid Zod schema expression. The output starts with `z.` and produces a complete schema that could be assigned to a variable or exported from a module.

**Example input:** "a user with name (string, required), email (string, valid email format, required), age (number, integer, optional, between 0 and 150), role (one of admin, user, guest), and addresses (array of objects with street, city, state, and zip code)"

**Example output:**
```typescript
z.object({
  name: z.string(),
  email: z.string().email(),
  age: z.number().int().min(0).max(150).optional(),
  role: z.enum(["admin", "user", "guest"]),
  addresses: z.array(
    z.object({
      street: z.string(),
      city: z.string(),
      state: z.string(),
      zip: z.string(),
    })
  ),
})
```

**Validation approach:** Syntax parsing of the code string. Optionally, `eval` in a sandboxed context with `zod` available to produce an actual ZodType object and catch runtime errors.

**Limitations:** The generated code string cannot express Zod features that require runtime closures or external references, such as `.refine()` with a function body that references external variables, `.transform()` with complex logic, or `z.lazy()` with recursive references that require a specific variable name. The generated `.refine()` calls use inline arrow functions with self-contained logic.

### JSON Schema

**What is generated:** A valid JSON Schema object. The output is a JSON string that parses to an object conforming to JSON Schema draft-07 or draft-2020-12 (configurable, default: draft-07).

**Example input:** Same as above.

**Example output:**
```json
{
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "email": { "type": "string", "format": "email" },
    "age": { "type": "integer", "minimum": 0, "maximum": 150 },
    "role": { "type": "string", "enum": ["admin", "user", "guest"] },
    "addresses": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "street": { "type": "string" },
          "city": { "type": "string" },
          "state": { "type": "string" },
          "zip": { "type": "string" }
        },
        "required": ["street", "city", "state", "zip"]
      }
    }
  },
  "required": ["name", "email", "role", "addresses"]
}
```

**Validation approach:** JSON parse, then meta-schema validation. The meta-schema check verifies structural correctness: `type` values are valid JSON Schema types, `properties` is an object, `required` is an array of strings referencing existing properties, `items` is present on array types, nested objects have their own `type: "object"` declarations.

**Limitations:** JSON Schema cannot express all constraints that Zod can (custom refinements, transforms, lazy recursive types with arbitrary logic). The generated JSON Schema covers types, formats (`email`, `uri`, `uuid`, `date-time`, `date`, `ipv4`, `ipv6`), numeric constraints (`minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`), string constraints (`minLength`, `maxLength`, `pattern`), array constraints (`minItems`, `maxItems`, `uniqueItems`), and enums. Complex business logic constraints ("password must contain uppercase and number") are expressed as `pattern` where possible or noted in `description` fields where not.

### TypeScript Type

**What is generated:** A TypeScript interface or type alias declaration. For object types, an `interface` is generated. For union types, enum types, or types that cannot be expressed as an interface, a `type` alias is generated. Nested object types are extracted as separate named interfaces when they are referenced by name in the description.

**Example input:** Same as above.

**Example output:**
```typescript
interface Address {
  street: string;
  city: string;
  state: string;
  zip: string;
}

interface User {
  name: string;
  email: string;
  age?: number;
  role: "admin" | "user" | "guest";
  addresses: Address[];
}
```

**Validation approach:** Syntax check for balanced braces, valid declaration keywords, valid type expressions, and valid property declarations. Does not involve the TypeScript compiler.

**Limitations:** TypeScript types are purely structural -- they carry no runtime validation logic. Constraints like "min 0, max 150" or "valid email" cannot be expressed in TypeScript types. The generated type captures the shape of the data (which fields exist, their types, optionality) but not the validation rules. Developers who need runtime validation should use the Zod or JSON Schema output formats.

### All Formats

When `format: 'all'` is specified, all three formats are generated from a single description. This is implemented as three sequential LLM calls (one per format), not a single call asking for all three. Separate calls produce higher quality output because each prompt is optimized for its specific format without conflicting instructions. The result object contains all three outputs:

```typescript
const result = await generateSchema("a user with name and email", {
  llm,
  format: "all",
});
// result.zod    → { code: "z.object({ ... })" }
// result.jsonSchema → { schema: { type: "object", ... } }
// result.typescript → { code: "interface User { ... }" }
```

## 7. LLM Prompt Design

### System Prompt

The system prompt establishes the LLM's role and the rules for schema generation. It is format-specific -- different system prompts are used for Zod, JSON Schema, and TypeScript generation. The system prompt is not configurable by the caller because it contains carefully tuned instructions that maximize generation reliability.

**Zod system prompt (summary of content):**
- Role: "You are a schema generator that produces valid Zod schemas from natural language descriptions."
- API coverage: List the Zod methods the model may use -- `z.object`, `z.string`, `z.number`, `z.boolean`, `z.array`, `z.enum`, `z.literal`, `z.union`, `z.discriminatedUnion`, `z.tuple`, `z.record`, `z.any`, `z.unknown`, `z.null`, `z.undefined`, `z.void`, `z.date`, `z.bigint`. Chainable methods: `.optional()`, `.nullable()`, `.default()`, `.describe()`, `.min()`, `.max()`, `.length()`, `.email()`, `.url()`, `.uuid()`, `.regex()`, `.trim()`, `.int()`, `.positive()`, `.negative()`, `.nonnegative()`, `.nonpositive()`, `.finite()`, `.refine()`, `.transform()`.
- Output rules: Output only the Zod expression starting with `z.`. No variable assignment, no imports, no explanation, no markdown fences.
- Type inference rules: When the description says "optional", use `.optional()`. When it says "required" or gives no optionality indication, make the field required. When it says "email", use `.email()`. When it gives numeric bounds, use `.min()` and `.max()`. When it lists enum values, use `z.enum([...])`.

**JSON Schema system prompt (summary of content):**
- Role: "You are a schema generator that produces valid JSON Schema from natural language descriptions."
- Draft version: Generate draft-07 by default (configurable to draft-2020-12).
- Structure rules: Root must have `type: "object"`. Every object must have `properties` and `required`. Array types must have `items`. Use `format` for well-known string formats. Use `enum` for fixed value sets.
- Output rules: Output only valid JSON. No prose, no explanation, no markdown fences.

**TypeScript system prompt (summary of content):**
- Role: "You are a type generator that produces valid TypeScript interface and type declarations from natural language descriptions."
- Style rules: Use `interface` for object types. Use `type` alias for unions and non-object types. Extract nested objects as separate named interfaces. Use `?` for optional fields. Use string literal unions for enums (e.g., `"admin" | "user"`).
- Output rules: Output only the TypeScript declarations. No runtime code, no imports, no explanation.

### Few-Shot Examples

Each system prompt includes two to three few-shot examples that demonstrate the expected input-output mapping. Examples are selected based on structural hints detected in the description (Step 1 of the pipeline). The example set covers the most common patterns:

**Example 1 -- Simple flat object:**
- Input: "a product with name (string), price (number, positive), and inStock (boolean)"
- Zod output: `z.object({ name: z.string(), price: z.number().positive(), inStock: z.boolean() })`

**Example 2 -- Object with optional fields and enums:**
- Input: "a task with title (string, required), description (string, optional), priority (one of low, medium, high), and completed (boolean, default false)"
- Zod output: `z.object({ title: z.string(), description: z.string().optional(), priority: z.enum(["low", "medium", "high"]), completed: z.boolean().default(false) })`

**Example 3 -- Nested objects and arrays:**
- Input: "an order with orderId (string, UUID format), items (array of objects with productId, name, quantity integer min 1, and unitPrice number), and total (number)"
- Zod output: `z.object({ orderId: z.string().uuid(), items: z.array(z.object({ productId: z.string(), name: z.string(), quantity: z.number().int().min(1), unitPrice: z.number() })), total: z.number() })`

These examples serve as templates that the LLM can pattern-match against. They demonstrate naming conventions (camelCase field names), constraint application (`.email()`, `.min()`, `.uuid()`), optionality handling (`.optional()`, `.default()`), and nesting patterns (arrays of objects).

### Output Format Constraints

The prompt ends with an explicit output constraint that minimizes post-processing:

```
Output ONLY the [Zod schema expression / JSON Schema object / TypeScript declarations].
Do not include any explanation, commentary, variable assignments, import statements, or markdown code fences.
Start your response directly with [z. / { / interface or type].
```

This instruction is repeated at the end of the prompt (after the description) because LLMs weight the end of the prompt more heavily than the middle. Despite this instruction, LLMs sometimes add prose or fences, which is why Step 4 (Extract Schema) exists.

### Handling Ambiguity

When the description is ambiguous, the LLM must make reasonable default decisions. The system prompt includes guidance for common ambiguities:

| Ambiguous Description | Default Interpretation | Rationale |
|---|---|---|
| "name" (no type specified) | `string` | Names are almost always strings. |
| "age" (no type specified) | `number` | Ages are numeric. Use `.int()` if "age" is mentioned. |
| "active" (no type specified) | `boolean` | Words like "active", "enabled", "visible", "completed" imply booleans. |
| "items" (no type specified) | `array` | Plural nouns suggest arrays. |
| "address" (no type specified) | `object` | Compound nouns suggest nested objects. |
| No optionality specified | `required` | Fields are required by default unless the description says "optional". |
| "id" (no format specified) | `string` | IDs are strings. If "UUID" is mentioned, add `.uuid()`. |
| "date" or "timestamp" | `string` with date format | Use `.datetime()` for Zod, `"format": "date-time"` for JSON Schema. |
| "email" as a field name | `string` with email validation | Field names like "email", "emailAddress" imply `.email()`. |
| "url" or "website" | `string` with URL validation | Field names like "url", "website", "link" imply `.url()`. |

## 8. Schema Validation

### Zod Code Validation

Zod code validation operates in two modes: syntax-only (the default) and eval-based (opt-in).

**Syntax-only validation** parses the generated code string as a JavaScript expression using a lightweight parser. It checks:

1. **Balanced delimiters**: Every `(` has a matching `)`, every `{` has a matching `}`, every `[` has a matching `]`. Unmatched delimiters are the most common LLM syntax error.
2. **Valid method chains**: Method calls after `z.` use known Zod method names. Unknown methods (e.g., `z.text()`, `z.integer()`) are flagged.
3. **Valid argument types**: String arguments to methods like `z.enum()` and `z.literal()` are valid string literals. Numeric arguments to `.min()` and `.max()` are valid numbers.
4. **No stray tokens**: The expression ends cleanly after the final closing delimiter. Trailing prose, semicolons, or additional statements are detected.

**Eval-based validation** (when `validate: 'eval'` is set) evaluates the code string in a sandboxed scope where `z` is the Zod library. This catches errors that syntax parsing misses:

- `.email()` called on a number schema (Zod throws at schema construction time).
- `.min("abc")` with a non-numeric argument to a numeric constraint.
- `z.enum([])` with an empty enum array (Zod requires at least one value).
- `.refine()` with a malformed function expression.

Eval-based validation requires `zod` to be installed as a peer dependency. If `validate: 'eval'` is set and `zod` is not installed, the package throws a clear error at configuration time.

The eval is performed using `new Function()` with a restricted scope. The only variable available in the scope is `z` (the Zod library). No access to `process`, `require`, `import`, `globalThis`, `fetch`, or any other global. This prevents the LLM output from executing arbitrary code.

### JSON Schema Validation

JSON Schema validation uses a built-in lightweight meta-schema validator. It does not require `ajv` as a dependency.

The validator checks:

1. **Valid JSON**: The output parses as valid JSON via `JSON.parse`.
2. **Root type**: The root schema has a `type` property with a valid JSON Schema type value (`"object"`, `"array"`, `"string"`, `"number"`, `"integer"`, `"boolean"`, `"null"`) or a valid composition keyword (`anyOf`, `oneOf`, `allOf`).
3. **Object schema structure**: If `type` is `"object"`, `properties` is an object (if present), `required` is an array of strings (if present), and every string in `required` exists as a key in `properties`.
4. **Array schema structure**: If `type` is `"array"`, `items` is present and is a valid schema.
5. **Enum values**: If `enum` is present, it is a non-empty array.
6. **Nested schema validity**: Every schema referenced in `properties`, `items`, `anyOf`, `oneOf`, `allOf`, `$defs`, and `definitions` is recursively validated.
7. **$ref resolution**: If `$ref` is present, it points to a path that exists in `$defs` or `definitions`.

If `ajv` is installed, the package can optionally use it for full meta-schema validation by setting `validate: 'strict'`. This provides comprehensive JSON Schema spec compliance checking.

### TypeScript Type Validation

TypeScript validation is the lightest of the three formats. It checks structural correctness without invoking the TypeScript compiler:

1. **Declaration keyword**: The output starts with `interface`, `type`, or `export` (followed by `interface` or `type`).
2. **Balanced braces**: Every `{` has a matching `}`.
3. **Property syntax**: Inside an interface body, each line matches the pattern `name: Type;` or `name?: Type;` (with allowances for multiline types, generics, and inline object types).
4. **Valid type expressions**: Type expressions use valid TypeScript type syntax -- primitive types (`string`, `number`, `boolean`, `null`, `undefined`), array types (`T[]` or `Array<T>`), union types (`A | B`), intersection types (`A & B`), literal types (`"value"`, `42`, `true`), tuple types (`[A, B]`), and object types (`{ key: Type }`).
5. **Multiple declarations**: If the output contains multiple interface/type declarations (common when nested types are extracted), each is individually validated.

### Custom Validator

The caller can provide a custom validator function that receives the extracted output string and returns a validation result:

```typescript
const result = await generateSchema("a user with name and email", {
  llm,
  format: "zod",
  validator: (code: string) => {
    if (code.includes('.transform(')) {
      return {
        valid: false,
        errors: ["Do not use .transform() — only pure validation schemas are allowed."],
      };
    }
    return { valid: true };
  },
});
```

The custom validator runs after the built-in format validator. Both must pass for the output to be accepted.

## 9. Schema Refinement

### Purpose

Schema refinement enables iterative schema development. Instead of writing a perfect description on the first attempt, the developer generates a base schema and then refines it with targeted modifications. This mirrors how developers actually work: start with a rough shape, then add constraints, rename fields, adjust types, and add validation rules.

### Refinement API

```typescript
import { refine } from 'schema-from-text';

// Start with a generated schema
const base = await generateZod("a user with name and email", { llm });
// base.code → 'z.object({ name: z.string(), email: z.string() })'

// Refine: add email validation
const v2 = await refine(base.code, "add email format validation to the email field", {
  llm,
  format: "zod",
});
// v2.code → 'z.object({ name: z.string(), email: z.string().email() })'

// Refine: add a role field
const v3 = await refine(v2.code, "add a required role field with enum values admin, user, guest", {
  llm,
  format: "zod",
});
// v3.code → 'z.object({ name: z.string(), email: z.string().email(), role: z.enum(["admin", "user", "guest"]) })'

// Refine: make name more constrained
const v4 = await refine(v3.code, "add min length 1 and max length 100 to the name field", {
  llm,
  format: "zod",
});
// v4.code → 'z.object({ name: z.string().min(1).max(100), email: z.string().email(), role: z.enum(["admin", "user", "guest"]) })'
```

### How Refinement Works

The `refine` function constructs a prompt that includes the existing schema and the modification instruction:

```
You are a schema modifier. You will be given an existing [Zod schema / JSON Schema / TypeScript type] and a modification instruction. Apply the modification to the schema and return the complete updated schema.

Existing schema:
[existing schema code/JSON]

Modification:
[modification instruction]

Return ONLY the complete modified schema. Do not return a partial schema or a diff. Include all existing fields and constraints, plus the requested modification.
```

The LLM receives the full existing schema, not just the part being modified. This ensures the LLM returns a complete updated schema rather than a fragment. The output is validated using the same pipeline as initial generation.

### Supported Modifications

Refinement supports any modification that can be expressed in natural language:

| Category | Example Modification |
|---|---|
| Add a field | "add a required createdAt field as a date string" |
| Remove a field | "remove the middleName field" |
| Change a type | "change the age field from string to number" |
| Add a constraint | "add min length 8 to the password field" |
| Remove a constraint | "remove the max length constraint from the name field" |
| Change optionality | "make the phone field optional" or "make the email field required" |
| Add validation | "add email format validation to the contactEmail field" |
| Add an enum | "change the status field to an enum with values active, inactive, suspended" |
| Rename a field | "rename the userName field to username" |
| Add nesting | "convert the address fields (street, city, zip) into a nested address object" |
| Add array | "change the tag field to an array of strings" |
| Add description | "add a description 'User ID in UUID format' to the id field" |

### Refinement Validation

The refined schema is validated through the same pipeline as an initial generation (Step 5). Additionally, `refine` optionally checks that the modification was actually applied -- if the output is identical to the input, it is considered a failure (the LLM did not understand or apply the modification). This check is enabled by default and can be disabled with `checkModified: false`.

## 10. Type Inference from Descriptions

This section documents the heuristics that guide the LLM's type inference when the description does not explicitly specify types. These heuristics are encoded in the system prompt's instructions and few-shot examples.

### Field Name to Type Mapping

| Field Name Pattern | Inferred Type | Zod | JSON Schema |
|---|---|---|---|
| `name`, `title`, `label`, `description`, `message`, `text`, `comment`, `note` | string | `z.string()` | `{ "type": "string" }` |
| `email`, `emailAddress` | string with email format | `z.string().email()` | `{ "type": "string", "format": "email" }` |
| `url`, `website`, `link`, `href`, `imageUrl`, `avatarUrl` | string with URL format | `z.string().url()` | `{ "type": "string", "format": "uri" }` |
| `id`, `userId`, `orderId`, `productId` | string | `z.string()` | `{ "type": "string" }` |
| `uuid`, `guid` | string with UUID format | `z.string().uuid()` | `{ "type": "string", "format": "uuid" }` |
| `age`, `count`, `quantity`, `amount`, `total`, `price`, `score`, `rating`, `size`, `width`, `height`, `weight` | number | `z.number()` | `{ "type": "number" }` |
| `active`, `enabled`, `visible`, `completed`, `verified`, `approved`, `published`, `deleted`, `isAdmin`, `hasAccess` | boolean | `z.boolean()` | `{ "type": "boolean" }` |
| `items`, `tags`, `categories`, `roles`, `permissions`, `addresses`, `emails`, `phones` | array | `z.array(...)` | `{ "type": "array", "items": ... }` |
| `address`, `location`, `config`, `settings`, `metadata`, `profile`, `preferences` | object | `z.object({...})` | `{ "type": "object", "properties": ... }` |
| `createdAt`, `updatedAt`, `deletedAt`, `startDate`, `endDate`, `birthDate`, `timestamp`, `date` | string with date-time format | `z.string().datetime()` | `{ "type": "string", "format": "date-time" }` |
| `phone`, `phoneNumber`, `mobile` | string | `z.string()` | `{ "type": "string" }` |
| `zip`, `zipCode`, `postalCode` | string | `z.string()` | `{ "type": "string" }` |

### Constraint Keyword Detection

| Keyword in Description | Applied Constraint | Zod | JSON Schema |
|---|---|---|---|
| "optional" | Field is optional | `.optional()` | Omitted from `required` array |
| "required" | Field is required | (default -- no modifier) | Included in `required` array |
| "at least N" or "min N" or "minimum N" | Minimum value/length | `.min(N)` | `"minimum": N` or `"minLength": N` |
| "at most N" or "max N" or "maximum N" | Maximum value/length | `.max(N)` | `"maximum": N` or `"maxLength": N` |
| "between N and M" | Range constraint | `.min(N).max(M)` | `"minimum": N, "maximum": M` |
| "positive" | Greater than 0 | `.positive()` | `"exclusiveMinimum": 0` |
| "negative" | Less than 0 | `.negative()` | `"exclusiveMaximum": 0` |
| "integer" or "whole number" | Integer constraint | `.int()` | `"type": "integer"` |
| "email" or "email format" | Email format | `.email()` | `"format": "email"` |
| "URL" or "url format" | URL format | `.url()` | `"format": "uri"` |
| "UUID" or "uuid format" | UUID format | `.uuid()` | `"format": "uuid"` |
| "unique" (in array context) | Unique items | (custom `.refine()`) | `"uniqueItems": true` |
| "non-empty" (string) | Min length 1 | `.min(1)` | `"minLength": 1` |
| "non-empty" (array) | Min items 1 | `.min(1)` | `"minItems": 1` |
| "nullable" | Can be null | `.nullable()` | `"type": ["string", "null"]` |
| "default X" | Default value | `.default(X)` | `"default": X` |

### Enum Detection

Enums are detected by several natural language patterns:

| Pattern | Example | Output |
|---|---|---|
| "one of: A, B, C" | "status: one of active, inactive, suspended" | `z.enum(["active", "inactive", "suspended"])` |
| "either A or B" | "type: either credit or debit" | `z.enum(["credit", "debit"])` |
| "A, B, or C" (in type position) | "priority: low, medium, or high" | `z.enum(["low", "medium", "high"])` |
| "enum: A, B, C" | "role enum: admin, user, guest" | `z.enum(["admin", "user", "guest"])` |
| "values: A, B, C" | "status with values pending, approved, rejected" | `z.enum(["pending", "approved", "rejected"])` |

### Array and Nesting Detection

| Pattern | Example | Output |
|---|---|---|
| "array of X" | "array of strings" | `z.array(z.string())` |
| "list of X" | "list of user objects" | `z.array(z.object({...}))` |
| "X items" | "tag items" | `z.array(...)` |
| "multiple X" | "multiple email addresses" | `z.array(z.string().email())` |
| "X with fields" | "address with street, city, zip" | `z.object({ street: ..., city: ..., zip: ... })` |
| "X containing" | "config containing host, port, debug" | `z.object({ host: ..., port: ..., debug: ... })` |
| "each having" / "each with" | "items, each having name and price" | `z.array(z.object({ name: ..., price: ... }))` |
| "nested X" | "nested address object" | `z.object({...})` (inline) |

## 12. LLM Interface

### Simple Function Signature

The LLM interface is a single function: `(prompt: string) => Promise<string>`. This is the simplest possible abstraction that still supports every LLM provider, local model, and custom inference server. The caller wraps their provider SDK call in this function. `schema-from-text` constructs the prompt and receives the response -- it has no knowledge of the provider, model, temperature, or any other generation parameter.

### Adapter Examples

**OpenAI:**

```typescript
import OpenAI from 'openai';

const openai = new OpenAI();

### Retry Behavior

When the LLM returns output that fails validation, `schema-from-text` retries by calling the LLM function again with an expanded prompt that includes error feedback. The retry is at the output-validation level, not the API level. `schema-from-text` does not handle HTTP 429 rate limits, 5xx server errors, or network failures -- those are the caller's responsibility (the LLM function should handle its own transient error retries, or the caller can use `llm-retry` for the outer API-level retry).

The retry prompt is constructed as described in Section 5, Step 7. The maximum number of retries is configurable (default: 3). After the maximum retries are exhausted, the result is returned with `success: false` and the validation errors from the final attempt.

## 13. Configuration

### Default Configuration

| Option | Default | Description |
|---|---|---|
| `format` | `"zod"` | Output format. |
| `maxRetries` | `3` | Maximum validation retry attempts. |
| `validate` | `"syntax"` | Validation mode for Zod output. |
| `jsonSchemaDraft` | `"draft-07"` | JSON Schema draft version. |
| `name` | `undefined` (LLM infers) | Name for the generated type/interface. |
| `checkModified` | `true` | Whether `refine` checks that the output changed. |

### Configuration Precedence

When using the `createGenerator` factory, options are resolved in this order (later overrides earlier):

1. Built-in defaults (table above).
2. `GeneratorConfig` passed to `createGenerator`.
3. Per-call options passed to `generator.generate()` or `generator.refine()`.

For example:

```typescript
const generator = createGenerator({
  llm,
  format: "json-schema",    // default format for this generator
  maxRetries: 5,             // default retry count for this generator
});

// Uses json-schema format and 5 retries (from generator config)
const r1 = await generator.generate("a user with name");

// Overrides format to zod, keeps 5 retries from generator config
const r2 = await generator.generate("a user with name", { format: "zod" });

// Overrides both format and retries
const r3 = await generator.generate("a user with name", { format: "typescript", maxRetries: 2 });
```

### CLI Binary Name

`schema-from-text`

### Commands and Flags

The CLI has no subcommands. It accepts a description as a positional argument or via stdin, and outputs the generated schema to stdout.

```
Usage: schema-from-text [options] <description>

Arguments:
  description                     Natural language description of the data structure

Options:
  -f, --format <format>           Output format: zod, json-schema, typescript, all (default: "zod")
  -o, --output <file>             Write output to a file instead of stdout
  -n, --name <name>               Name for the generated type/interface
  -r, --retries <count>           Maximum retry attempts (default: 3)
  --provider <provider>           LLM provider: openai, anthropic (default: "openai")
  --model <model>                 Model name (default: provider-specific default)
  --api-key <key>                 API key (default: read from env var)
  --validate <mode>               Validation mode for Zod: syntax, eval (default: "syntax")
  --json-schema-draft <draft>     JSON Schema draft: draft-07, draft-2020-12 (default: "draft-07")
  --refine <schema-file>          Refine an existing schema from a file
  --modification <instruction>    Modification instruction for --refine
  -q, --quiet                     Suppress non-schema output (no progress, no stats)
  -v, --version                   Show version
  -h, --help                      Show help
```

### CLI LLM Integration

The CLI includes built-in LLM adapters for OpenAI and Anthropic. API keys are read from environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`) or passed via the `--api-key` flag. The CLI uses the selected provider's SDK to make the LLM call.

```bash
# Using OpenAI (default)
export OPENAI_API_KEY=sk-...
schema-from-text "a user with name, email, and optional phone"

# Using Anthropic
export ANTHROPIC_API_KEY=sk-ant-...
schema-from-text --provider anthropic "a user with name, email, and optional phone"

# JSON Schema output to file
schema-from-text -f json-schema -o user-schema.json "a user with name and email"

# TypeScript output
schema-from-text -f typescript "a user with name, email, and optional age"

# Refine an existing schema
schema-from-text --refine ./user-schema.ts --modification "add a role enum with admin, user, guest"

# Pipe description from stdin
echo "a product with name, price, and tags" | schema-from-text -f zod
```

### CLI Output

When writing to stdout (no `--output` flag), the CLI outputs only the generated schema code/JSON. Progress messages and statistics are written to stderr so they do not interfere with piping:

```bash
# Pipe directly to a file
schema-from-text "a user with name and email" > user-schema.ts

# Pipe to clipboard (macOS)
schema-from-text "a user with name and email" | pbcopy
```

When `--quiet` is set, only the schema is output (no progress, no retry messages, no statistics).

### Exit Codes

| Code | Meaning |
|---|---|
| `0` | Schema generated successfully. |
| `1` | Schema generation failed after all retries. |
| `2` | Configuration or usage error (invalid flags, missing API key, missing description). |

## 15. Integration with Monorepo Packages

### schema-bridge

`schema-from-text` generates schemas from natural language. `schema-bridge` converts schemas between provider-specific formats. The two compose naturally: generate a schema from text, then convert it to the format a specific LLM provider expects.

```typescript
import { generateJSONSchema } from 'schema-from-text';
import { bridge } from 'schema-bridge';

// Generate a JSON Schema from text
const result = await generateJSONSchema(
  "tool parameters: query (string, required), maxResults (number, optional, default 10)",
  { llm },
);

if (result.success) {
  // Convert to OpenAI tool format
  const openaiSchema = bridge(result.schema, "openai");

  // Convert to Anthropic tool format
  const anthropicSchema = bridge(result.schema, "anthropic");
}
```

### llm-retry

`schema-from-text` implements its own lightweight retry loop (call LLM, validate, retry with error feedback). For advanced retry needs -- escalation strategies, API-level retry with backoff, custom repair functions -- the caller can use `llm-retry` externally to wrap the LLM function before passing it to `schema-from-text`.

```typescript
import { generateZod } from 'schema-from-text';
import { createRetryLoop } from 'llm-retry';

// Use llm-retry for API-level retry (429, 5xx)
const retryLoop = createRetryLoop({
  callLLM: async (messages) => {
    const response = await openai.chat.completions.create({
      model: "gpt-4o-mini",
      messages,
    });
    return response.choices[0].message.content ?? "";
  },
  maxRetries: 3,
  apiRetry: { enabled: true, maxRetries: 5 },
});

// Wrap llm-retry as a simple LLM function for schema-from-text
const llm = async (prompt: string): Promise<string> => {
  const result = await retryLoop.execute([
    { role: "user", content: prompt },
  ]);
  return result.success ? JSON.stringify(result.data) : "";
};

const schema = await generateZod("a user with name and email", { llm });
```

### tool-output-guard

Schemas generated by `schema-from-text` can be passed directly to `tool-output-guard` for runtime validation of tool outputs.

```typescript
import { generateZod } from 'schema-from-text';
import { guard } from 'tool-output-guard';

const result = await generateZod(
  "tool output: temperature (number), conditions (string), humidity (number, 0-100)",
  { llm, validate: "eval" },
);

if (result.success && result.schema) {
  // Use the generated Zod schema for runtime validation
  const validate = guard(result.schema);
  const output = validate({ temperature: 72, conditions: "sunny", humidity: 45 });
}
```

### prompt-price

For cost-aware schema generation, `prompt-price` can estimate the cost of each LLM call before making it.

```typescript
import { generateZod } from 'schema-from-text';
import { estimatePrice } from 'prompt-price';

const description = "a complex order with nested items, shipping address, and billing info";

// Estimate cost before generating
const estimate = estimatePrice({
  model: "gpt-4o-mini",
  inputText: description,
  estimatedOutputTokens: 500,
});

console.log(`Estimated cost: $${estimate.totalCost.toFixed(4)}`);

const result = await generateZod(description, { llm });
```

## 16. Testing Strategy

### Unit Tests

| Category | What Is Tested | Example |
|---|---|---|
| Description parsing | Structural hint detection from description strings | "array of users" detects array pattern; "optional age" detects optionality |
| Prompt construction | System prompt + few-shot + description assembled correctly per format | Zod prompt includes `z.object` example; JSON Schema prompt includes `"type": "object"` example |
| Output extraction | Markdown fence stripping, JSON extraction, prose removal | `` ```json\n{"type":"object"}\n``` `` extracts `{"type":"object"}` |
| Zod syntax validation | Valid and invalid Zod code strings | `z.object({ name: z.string() })` passes; `z.object({ name: z.string()` fails (unmatched paren) |
| JSON Schema validation | Valid and invalid JSON Schema objects | Complete schema passes; schema with `"required": ["nonexistent"]` fails |
| TypeScript validation | Valid and invalid TypeScript declarations | `interface User { name: string; }` passes; `interface User { name: }` fails |
| Retry prompt construction | Error feedback message contains errors and original output | Feedback includes "Syntax error at position 45" and the invalid output |
| Result object construction | Success and failure results have correct fields | Success result has `success: true`, `code` field, `attempts: 1` |

### Integration Tests

Integration tests use a mock LLM function that returns predetermined responses. This tests the full pipeline without making real API calls.

| Scenario | Mock LLM Behavior | Expected Outcome |
|---|---|---|
| Success on first attempt | Returns valid Zod code | `success: true`, `attempts: 1` |
| Success on retry | Returns invalid code, then valid code on retry | `success: true`, `attempts: 2` |
| Failure after max retries | Returns invalid code on every attempt | `success: false`, `attempts: 4` (1 initial + 3 retries) |
| JSON Schema generation | Returns valid JSON Schema | `success: true`, `schema` is a valid object |
| TypeScript generation | Returns valid TypeScript | `success: true`, `code` contains `interface` |
| All formats | Returns valid output for each format call | `zod`, `jsonSchema`, and `typescript` fields all populated |
| Refinement | Returns modified schema on refinement | `success: true`, output differs from input |
| Output with markdown fences | Returns valid code wrapped in ` ``` ` | Extraction strips fences, validation passes |
| Output with prose | Returns "Here is the schema:" followed by valid code | Extraction strips prose, validation passes |
| Custom validator | Valid code but custom validator rejects `.transform()` | `success: false`, error from custom validator |
| Abort signal | Signal aborted during LLM call | `success: false`, result indicates cancellation |

### End-to-End Tests

End-to-end tests make real LLM API calls (gated behind an environment variable `RUN_E2E_TESTS=true`) and verify that the full pipeline produces valid, usable schemas.

| Test | Description | Validation |
|---|---|---|
| Simple Zod generation | "a user with name and email" | Generated code parses as valid Zod; `eval`'d schema validates `{ name: "Alice", email: "a@b.com" }` |
| Complex nested Zod | "an order with items array, shipping address, billing address" | Generated code produces a multi-level schema; `eval`'d schema validates a sample order object |

## 17. Performance

### Latency

Schema generation latency is dominated by LLM API call time. The `schema-from-text` package itself adds negligible overhead:

| Operation | Expected Latency |
|---|---|
| Description parsing | < 1ms |
| Prompt construction | < 1ms |
| Output extraction | < 1ms |
| Zod syntax validation | < 5ms |
| JSON Schema validation | < 5ms |
| TypeScript validation | < 2ms |
| Zod eval validation | < 50ms (requires Zod library load) |

Total package overhead per attempt: < 10ms (syntax validation) or < 60ms (eval validation). LLM API latency (typically 500ms - 5000ms) dominates.

### Retry Cost

Each retry doubles the effective cost and latency of the generation. With `maxRetries: 3`, worst-case cost is 4x a single call (1 initial + 3 retries). In practice, models like GPT-4o and Claude Sonnet succeed on the first attempt for most descriptions. Retry rates increase for complex nested schemas, unusual constraint combinations, and weaker models.

| Scenario | Expected First-Attempt Success Rate |
|---|---|
| Simple flat object (3-5 fields) | 95%+ |
| Object with enums and optional fields | 90%+ |
| Nested objects (1 level) | 85%+ |
| Arrays of nested objects | 80%+ |
| Complex schemas (3+ nesting levels, many constraints) | 70%+ |
| With eval validation (stricter) | 5-10% lower than syntax-only |

### Token Usage

Prompt size depends on the description length and the format. The system prompt, few-shot examples, and output instructions add a fixed overhead:

| Component | Approximate Token Count |
|---|---|
| System prompt (Zod) | 400-500 tokens |
| Few-shot examples (2-3) | 300-400 tokens |
| Output constraint | 50-100 tokens |
| User description | Varies (typically 20-200 tokens) |
| **Total input (first attempt)** | **800-1200 tokens** |
| Retry feedback (per retry) | 200-500 tokens (errors + previous output) |
| **Generated output** | **100-800 tokens** (depends on schema complexity) |

```typescript
